# F3.5 Design: The USB Session Guard

## 1. Purpose

Bind a running session to the **identity of the device a working directory lives on**, and report when that
binding stops holding.

The threat is a **mid-session device swap**: a user starts work on a USB drive, an attacker (or a careless
colleague) removes it and substitutes another. Without a guard, the session continues against the new
medium, and anything derived from a secret that lived on the old one is now operating on a device the user
did not choose.

The feature **detects and reports**; it does not exit. The caller owns its loop and drops its state — see §7
for why the responsibility is split that way and what that means for the time budget.

## 2. Public API

Two layers, in two crates. The split follows F3's: platform mechanisms in `tokengen-sys`, policy and the
caller-facing types in `tokengen`.

### `tokengen-sys::device` — the platform layer

```rust
pub fn resolve(path: &Path) -> Result<DeviceDescriptor, DeviceReadError>;
pub fn identify(device: &DeviceDescriptor) -> Result<DeviceIdentity, DeviceReadError>;
pub fn is_removable(device: &DeviceDescriptor) -> Result<bool, DeviceReadError>;
pub fn component_of(err: &DeviceReadError) -> Option<IdentityComponent>;
```

`DeviceDescriptor` is **opaque outside `tokengen-sys`** — its field is `pub(crate)` (the free functions in the
same crate need it), with no `Clone` and no `Debug`. It can only be produced by a successful `resolve`.

The opacity is load-bearing: it makes "a device that could not be resolved" unrepresentable, so no caller can
invent one and no test can fabricate one. **Precisely:** opaque to `tokengen`, which cannot see the field and
only passes `&device.inner` back into `tokengen-sys`; *not* opaque within `tokengen-sys` itself, where the
platform functions operate on the `RawDevice`. The narrower word "private" was wrong and is corrected here —
the distinction matters because it is what `ResolvedDevice` in `tokengen` relies on.

### `tokengen::session` — the guard

```rust
pub struct SessionGuard<R: DeviceReader> { /* private */ }

impl<R: DeviceReader> SessionGuard<R> {
    pub fn capture(reader: R, cwd: &Path) -> Result<(Self, GuardStatus), SessionError>;
    pub fn check(&self) -> GuardStatus;
    pub fn identity(&self) -> &DeviceIdentity;
}

pub trait DeviceReader {
    type Device;
    fn resolve(&self, path: &Path) -> Result<Self::Device, SessionError>;
    fn identify(&self, device: &Self::Device) -> Result<DeviceIdentity, SessionError>;
}

pub enum GuardStatus { Present, Missing, IdentityMismatch { expected, observed },
                       Unverifiable { component }, Disabled }
pub enum SessionError { NotOnRemovableDevice, DeviceNotFound,
                        IdentityUnreadable { component }, NotSupported }
pub struct SystemDeviceReader;   // the real reader
```

### The usage contract

```rust
let (guard, status) = SessionGuard::capture(SystemDeviceReader::new(), &cwd)?;
if !status.is_ok() { return; }          // only `Present` permits the session to continue

loop {
    match guard.check() {
        GuardStatus::Present => {}
        _ => { drop_secrets(); return; } // every other status aborts
    }
    // …at least every 250 ms, even while blocked on input (§7)
}
```

## 3. Why `capture` returns a tuple, not just a `Result`

`Disabled` — the `dev-mode` build — is a **legitimate status of a successfully constructed guard**, not an
error. A `Result`-only signature cannot express it, and would tempt a caller to treat "capture succeeded" as
"the session is guarded", which is exactly the false-assurance class this project treats as its worst defect.

The cost is that `#[must_use]` is now a **partial** guard, and that partiality is measured rather than
assumed:

* test 13a proves `SessionGuard::capture(r, p);` is **rejected** (compile-fail);
* test 13b proves `let (_guard, _status) = …;` **compiles silently** — a *passing* compile-fail case.

No `#[must_use]` inspects binding patterns, so the escape hatch cannot be closed. A suite testing only 13a
would leave it unmeasured and let a later reader believe the attribute is total. The failures table records
that exact prose claim being wrong once already.

## 4. Why the trait is keyed on a resolved device

A path-keyed interface cannot express *"the same path is now a different device"* — which is precisely the
swap under detection. It can only re-read strings. So `resolve` produces a device, and identity is read from
**that**, not from the path.

`DeviceReader` has an **associated `Device` type** rather than naming `ResolvedDevice` directly. The real
reader's `Device` is `ResolvedDevice` (still opaque); a test reader defines its own. Without this, the mock
could not exist without a public test-only constructor, which would weaken the very opacity the type exists
for. **No test-only constructor exists in the public API.**

**No `Clone` bound.** `check` binds the token by value and passes `&device` to `identify`; no copy is taken.
Requiring `Clone` would force it onto a token carrying a device identity — the reasoning that leaves F3's
`LockHandle` non-`Clone`.

## 5. Status semantics, and why `Unverifiable` is its own variant

| Status | Meaning | Caller action |
|---|---|---|
| `Present` | the bound device is present, identity matches | continue |
| `Missing` | the mount is gone | **abort** |
| `IdentityMismatch` | a real, *different* device is here | **abort** |
| `Unverifiable` | device may be present; identity unconfirmable | **abort** |
| `Disabled` | the guard is compiled off (`dev-mode`) | caller's choice, **never treated as `Present`** |

The three abort-worthy failures are distinguished because their **diagnostics** differ, not their
consequences. `IdentityMismatch` carries `expected` *and* `observed`; when a component cannot be read there
**is no observed value**, and fabricating one — an empty string, the mount path with a blank UUID — would
make the type assert something the system does not have.

> **The principle:** a status type must not be forced to carry a value the system does not have.

**And its mirror, learned the hard way (AM-006.2):** an **error** type must not be forced to *lose* a value
the system *does* have. A single `DeviceReadError::PropertyUnreadable` was returned by both the UUID lookup
and the serial read, and mapped unconditionally to `FilesystemUuid` — so a caller whose **serial** was
unreadable was told the **filesystem UUID** was. Measured on a Lexar flash drive: the by-uuid entry exists;
`device/serial` and `device/vpd_pg80` do not. The variants are now `UuidUnreadable` and `SerialUnreadable`,
so `component_of` is a total, correct mapping and the type states the fact rather than requiring every
producer to remember to label it.

A third variant, `RemovabilityUnreadable`, exists because removability is **neither** identity component:
`component_of` returns `None` for it, rather than naming a component that was read successfully.

### Fail-closed, stated as a property

Only `Present` permits the session to continue. `GuardStatus::is_ok()` exists so a caller cannot write
`if let Present = … {} else {}` and invert the default. **No path returns `Present` without having read and
compared a real identity**, and the platform error mapping is total with a catch-all that is an **error**,
never a default success.

## 6. The platform mechanism (Linux)

Three reads, each probed on real hardware:

| Component | Source | Probe |
|---|---|---|
| backing device | `stat().st_dev`, falling back to `st_rdev` for a device node, → `/sys/dev/block/<maj>:<min>` | P5, P7b |
| whole-disk reduction | **the kernel**: walk up from `/sys/dev/block/<maj>:<min>` while the directory holds a `partition` file | AM-006.1 |
| filesystem UUID | reverse traversal of `/dev/disk/by-uuid` | P5 |
| hardware serial | `/sys/block/<disk>/device/vpd_pg80` (the **disk's** ATA serial) | P3, P8, P11 |
| removability | the **transport**, not the kernel's `removable` flag | P10 |

### Whole-disk reduction is asked of the kernel (AM-006.1)

Reducing a partition to its disk was string manipulation, ending in `trim_end_matches(is_ascii_digit)`. **A
trailing digit is not evidence of a partition suffix:** `nvme0n1` and `mmcblk0` end in digits by naming
convention. Measured:

| input | old output | correct? |
|---|---|---|
| `nvme0n1p2` | `nvme0n1` | yes |
| `sda1` | `sda` | yes |
| **`nvme0n1`** | **`nvme0n`** | **no** |
| **`mmcblk0`** | **`mmcblk`** | **no** |

The kernel already knows: `/sys/block/<...>/partition` exists **only** for a partition. So the device's
sysfs directory is canonicalised via `/sys/dev/block/<maj>:<min>` and the code **walks up while it contains a
`partition` file**; the first directory without one is the disk.

**Two corrections were needed, and probes caught both** — recorded because the first draft of this very
section was wrong. `/sys/block` contains **only whole disks**, and a partition's directory is a child of its
disk's (`/sys/block/sda/sda1`, *not* `/sys/block/sda1`). An intermediate draft therefore returned partitions
unchanged and **broke `/dev/sda1`**, which had worked. Verified on six real paths before shipping.

Two of these were corrected after the first mechanism proved wrong:

**`st_dev` vs `st_rdev`.** A mounted filesystem path resolves through `st_dev`; a **device node** resolves
through `st_rdev`. Reading `st_dev` unconditionally returns `0:6` for `/dev/sda1` — the filesystem the node
lives on — which resolves to nothing. `device_of()` now prefers whichever resolves.

**Removability: a removable transport is sufficient; a fixed transport defers to the flag.**

A USB enclosure whose bridge presents a fixed disk reports `removable = 0`, indistinguishable by that flag from
an internal NVMe root. Measured on the maintainer's hardware: `sdb` (external, `RM=0`) and `nvme0n1` (internal
root, `RM=0`) are identical by the flag and separable by the transport. Deciding by the flag alone **refused a
legitimate external drive** — a false refusal, which is the failure a user notices.

**Stated precisely, because an earlier revision of this section said "the transport is authoritative" and that
is not what the code does** (Bruce's security review, Finding 1):

| transport | how removability is decided |
|---|---|
| `usb`, `mmc`, `thunderbolt`, `firewire` | **removable**, unconditionally — the flag is not consulted |
| `nvme`, `ata`, `sata`, `virtio` | **the kernel flag decides.** A fixed transport reporting `1` is accepted — that is the legitimate card-reader / media-slot case, and it is why this branch exists |
| unknown | the flag decides; if unreadable, **error** rather than guess |

So the flag is *secondary* only for a removable transport. For a **fixed** one it is decisive, and can accept
a device the transport rule alone would refuse. That is **by design**, and it is not exploitable without
kernel control — but a reader must not infer from the summary that a fixed-transport device can never be
accepted.

**A USB drive exposes two different serials.** `vpd_pg80` gives the **disk's** ATA serial; udev's
`ID_SERIAL_SHORT` gives the **enclosure bridge's**. They identify different components, and the choice
determines what "the same device" means. The guard binds to the **disk** serial — the medium the secret lives
on — because the alternative would bind a session to a piece of plastic a user may swap.

## 7. Poll model, and the G16 arithmetic

**Passive caller-polls.** No background thread, no `wait_for_change`, no shutdown coordination. F3.5
**detects**; the caller **exits**, because F3.5 does not own the caller's loop.

```
250 ms  caller polls at least this often          (a constraint F3.5 places on F4/F10)
+250 ms F3.5's detection budget                  <- asserted by test 10
+500 ms caller acts on the status (drop secrets) (F4's contract, NOT asserted by F3.5)
= 1.0 s  G16 satisfied
```

**Boundary of responsibility:** F3.5 asserts **detection** latency only. It never asserts *exit* latency. A
reader who saw "the latency test passes" must not conclude the end-to-end second is met — that needs F4's
test too. The budget is written down so the constraint is checkable from both sides.

`check` **never caches**. Every call re-resolves and re-identifies: a guard returning a remembered `Present`
would report on the past, which is the false-assurance class again. Measured: mock 74 ns, real ~170 µs.

## 8. `dev-mode`, and why it is mechanically enforced

A compile-time feature, **not** an environment variable: a guard disableable by ambient configuration is a
guard whose central guarantee is conditional (G1).

Under `dev-mode`, `capture` returns `GuardStatus::Disabled` — **never a silent `Present`**. Two mechanical
defences, because a rule only written down is a rule eventually broken:

1. `src/session.rs` **refuses to compile** with `dev-mode` unless `TOKENGEN_DEV_MODE_ACK=1` is set. A release
   build cannot acquire the guard-disabling path by accident.
2. CI asserts `dev-mode` is not in the `default` feature set, **and** that enabling it without the
   acknowledgement fails to build.

`dev-mode` is also built, linted and tested in CI, and the guard's test suite asserts **its own contract**
there (test 11: `Disabled`, never `Present`) rather than being skipped — a suite that silently skips reports a
pass while testing nothing.

## 9. Invariants

| Invariant | How it is met |
|---|---|
| G3 fail-closed | only `Present` permits continuation; every error is an error; the error mapping's catch-all is not a success |
| G16/G17 binding | identity from persistent device data, stable across re-plug (P11) and changing on substitution |
| G7 no external binaries | no `lsblk`/`udevadm`; sysfs read directly. The probes use host tools, the shipped code does not |
| G4 zeroize on drop | N/A here — this module holds no secret. `DeviceIdentity` is a device property, documented non-secret |
| G9 constant-time compare | **Does not apply, and the reason matters.** `observed == bound` short-circuits, so it *is* timing-sensitive — an earlier revision justified skipping G9 on the grounds that "this is not a secret comparison", which Bruce's review (Finding 2) correctly called too thin. The defensible reason is different: the identity is **not a credential**. It is a device property that must be *presented*, not *known* — an attacker who recovers the serial by timing gains nothing, because presenting a device that reports it requires custom firmware, and such an attacker can read the serial off the physical label more cheaply and exactly. Recorded because the conclusion survives while the original reasoning did not |
| `unsafe` confinement | three enumerated `tokengen-sys` modules; `src/` has no `allow(unsafe_code)` and no `unsafe` block |

## 10. Lint configuration

`GuardStatus` derives `Debug`, following F3's `MemoryLockStatus`: everything it carries is a device property
(uuid, serial) the project documents as **not secret**, so redaction is *structural* — no variant can hold key
material. `SessionGuard` is deliberately **not** `Debug` (it holds the reader and the binding), and not
`Send`/`Sync`/`Clone`.

`ResolvedDevice` has **no `Debug`**: a derived one would print *where the tool ran* into any formatted error,
against the posture of leaving no trace on the host. Use `DeviceIdentity` for diagnostics.

`DeviceReader`'s associated type has **no `Clone` bound** — see §4.

## 11. What F3.5 explicitly does NOT do

* **It does not exit.** It detects and reports; the caller acts. See §7.
* **It does not support macOS or Windows.** The backend is gated `#[cfg(target_os = "linux")]`; every other
  target takes a stub returning `NotSupported`. **This is a correction, not the original design:** the gate
  was `#[cfg(unix)]`, which is true on macOS, so macOS compiled a Linux backend whose `/sys` reads cannot
  work — and reported `DeviceNotFound` rather than `NotSupported`, asserting "the device you named does not
  exist" when the truth was that the platform has no backend (DEFECT-008).
* **It does not read a serial via `SG_IO`.** See W4 below; such drives fail closed.
* **It does not verify that the filesystem is intact**, only that the device is the same one.

## 12. Limitations — carried, with their basis **and their evidence class**

Each is stated with **how it is known**, because a limitation without its basis is a claim.

### The evidence class is part of the claim

Grace's verification condition (re-verification report): a limitation, and equally a *guarantee*, must say
whether it was **verified with hardware attached** or **verified in principle**. The distinction matters
because the two can diverge — and in this feature they did: every real-hardware result was obtained with two
USB drives attached, and **those drives were detached** for the re-verification run.

| Class | Means |
|---|---|
| **HW** | observed on real hardware, with the device attached, at a recorded commit |
| **Principle** | established without hardware — a pure function, a compile-time gate, or a code read. **Not** an observation of behaviour. |
| **Cited** | taken from documentation or a specification. The weakest; neither observed nor proved here. |

**A `Principle` result is not weaker than an `HW` one** — a total function over a public enum is fully
established by example. What would be wrong is presenting a `Principle` result as though a device had been
exercised, or an `HW` result as though it held everywhere.

### The limitations

| # | Limitation | Basis | Evidence class | Status |
|---|---|---|---|---|

### What was verified with hardware, and what is only established in principle

A summary, because the table above is per-limitation and this is per-guarantee:

| Guarantee | Verified with hardware? |
|---|---|
| a real USB drive is accepted, an internal root refused | **HW** — both drives, `/dev/sda1` and `/dev/sdb1` |
| identity survives a physical re-plug | **HW** — Probe P11 |
| a serial failure names `HardwareSerial` | **Principle** — the mapping is a pure function; the *observation* that exposed it was `HW`, but is not reproducible without the drives |
| whole-disk reduction (`nvme0n1`, and by rule `mmcblk0`) | **HW** — `nvme0n1` refused; `sda` and `sdb` (whole USB disks) accepted, at both granularities. Re-checked 2026-10-16 |
| only `Present` permits continuation; fail-closed everywhere | **HW** and **Principle** — real paths, plus mutation |
| the guard is `!Send`/`!Sync`; the `#[must_use]` boundary | **Principle** — compile-fail, which is the correct instrument |
| latency within the 250 ms budget | **HW** for the mock and real paths, with a drive attached |
| macOS/Windows take the stub | **Principle** (the gate) — **never executed** |

**The last row is the one to weigh before 1.0:** those platforms are compiled by CI on all three runners, but
their *device backends do not exist*, so nothing on them has been executed. That is W1/W2 and it is a
1.0 blocker, not a footnote.

## 13. Compilation targets and cfg branches

| Target | Backend |
|---|---|
| Linux | real (`/sys/dev/block`, `/sys/block/*/device/*`, `/dev/disk/by-uuid`) |
| macOS, Windows, everything else | stub → `NotSupported`, fail-closed |

`scripts/cfg_check.sh` compiles the **deferred** branch by textual inversion, so a stub whose signature drifts
from its callers fails a gate rather than surviving to a platform nobody builds locally. It matches attribute
**lines only** — an earlier revision matched gate strings anywhere in the file, so a comment could inflate the
count and the gate could invert prose while leaving the real gates untouched, reporting PASS on a tree it had
not modified.
